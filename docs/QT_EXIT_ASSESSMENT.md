# Qt 제거·재작성 영향도와 성능 검토

2026-11-04. 현재 Studio 작업 트리와 실제 빌드 산출물, 네이티브 성능 probe, 기존 웹 측정, 공식 플랫폼 문서를 확인했다. 제품 코드를 교체하지 않았으며 신규 엔진의 성능 향상률을 측정했다고 주장하지 않는다.

통합 실행 백로그는 [Qt-free 전환 태스크](QT_FREE_MIGRATION_TASKS.md)에 정리했다. 구현 시 우선순위·선행 조건·검증 게이트는 해당 문서를 따른다.

## 판단

모바일·태블릿 웹 UX, 반응형 패널, Studio/Win98 스킨이 핵심이면 HTML/CSS 기반 UI로 재작성하는 방향은 장기적인 이점이 있다. 다만 Qt를 제거하면 자동으로 브러시가 빨라지는 것은 아니다. 기존 네이티브의 래스터 연산은 빠르고, 현재 코어도 Qt 이미지·렌더링·코덱에 연결돼 있다. 기존 기능을 지키는 완전 제거는 UI 교체보다 훨씬 큰 편집기 이식이다.

권고는 작은 Qt-free 편집 경로를 기존 앱 옆에서 먼저 검증하는 것이다. TypeScript UI와 독립적인 문서/픽셀 엔진을 기본으로 검토하고, 측정상 필요한 계산만 Qt 없는 C++/Rust Wasm으로 옮긴다. 데스크톱 셸 선택은 같은 문서를 웹과 모바일에서 검증한 뒤 확정한다. 기존 앱은 전환 검증 동안 기준 구현으로 유지한다.

[앞선 UI 개선 계획](UI_EVOLUTION_PLAN.md)의 투명도·입력 소유권·파일 보존 계약은 재작성해도 그대로 필요하다.

## 1. 실제 Qt 의존성과 이식 범위

현재 `src/`는 합계 약 4,157줄이다. `canvas.cpp` 1,231줄, `mainwindow.cpp` 1,332줄, `document.cpp` 537줄이다. 줄 수는 테스트·호환성 검증 비용을 포함하지 않는다.

| 부분 | 현재 의존 | Qt 완전 제거 시 영향 |
| --- | --- | --- |
| 문서·Undo/Redo | State/Patch에 QImage, QColor, QString, QVector 사용; revision·예산·후보 확정 | 상태 모델과 공유 복사/차이 기록의 메모리 소유권을 다시 구현 |
| 브러시·지우개·채우기 | 픽셀 루프, QPainterPath·QPointF·QRgb·QImage | 수학은 참고 가능하나 현재 코드 그대로 독립 엔진으로 링크할 수 없음 |
| 도형·선택·확대·변형 | QPainter, QTransform, QPainterPath·마스크 | 경계·보간·반올림·합성 결과와 취소 동작 검증 필요 |
| 문자 | QTextEdit, QInputMethod, QFont·QTextDocument | DOM textarea/입력 조합과 래스터 확정으로 재구성. 새 텍스트의 렌더링 결과는 차이가 날 수 있음 |
| 이미지/프로젝트 IO | QImageReader/Writer, QIODevice, QDataStream | 코덱·방향 메타데이터·사전 크기 검사·RPAINT01 파서/인코더 이식 |
| 네이티브 저장/복구 | QSaveFile, QLockFile, QStandardPaths, 작업 future | 기존 파일의 안전한 교체·동시 실행·취소·복구 위치 인계를 대체 |
| UI | QWidget/QAction/QDockWidget·palette/QSS | 전체 재작성. DOM/CSS의 반응형·접근성·스킨을 직접 활용 가능 |
| 웹 브리지 | File/Blob/IndexedDB는 JS, 연결부는 Emscripten/QObject | JS 파일·복구 트랜잭션 로직은 재사용 가능. Module/HEAP 연결은 교체 |
| 빌드/배포 | Qt/Emscripten/CMake와 Qt 파일명을 가정한 stage 도구 | 새 프런트 빌드와 manifest 이행 필요. 현재 stage 도구를 그대로 쓰는 것은 불가 |
| 테스트 | Qt Test UI·코어, Playwright 웹 테스트 | 기대 동작·입력 파일은 활용 가능. 테스트 실행 코드와 UI 탐색은 이식 필요 |

`paintcore`가 Widgets를 모른다는 것과 Qt 독립이라는 것은 다르다. 브러시 엔진도 Document가 아니라 QWidget인 Canvas 내부에 있다. ‘UI만 웹으로 바꾸고 기존 코어는 그대로’라는 접근에서도 브러시·선택·문자 경계의 추출 작업이 필요하다.

## 2. 구조 선택지 비교

| 선택지 | 장점 | 주요 비용/한계 | 적합한 경우 |
| --- | --- | --- | --- |
| Qt 유지·적응형 UI 보완 | 기존 기능/저장/네이티브 성능 보존, 이행 위험 낮음 | Qt 내부의 터치·패널·접근성 대응과 웹 패키지 부담 유지 | 기존 데스크톱 기능을 빠르게 안정화 |
| DOM UI + Qt Core/Gui Wasm | UI 자유도를 높이며 문서/IO 일부 유지 | Qt 완전 제거가 아님. QtGui와 코덱·런타임은 남고 브러시 추출·픽셀 전달 필요 | 점진 전환, 한 번에 바꾸는 위험 축소 |
| Qt-free TypeScript 엔진 + DOM/Canvas | 웹·모바일·스킨 구성에 유리, 단일 웹 제품 구조 | 모든 편집 경로 이식. CPU 픽셀 루프·GC·메모리 소유권을 잘못 설계하면 퇴보 | 웹 중심의 장기 제품 |
| Qt-free C++/Rust 코어 Wasm + DOM UI | 무거운 계산을 독립 코어로 공유 가능 | 가장 큰 초기 설계/빌드 비용. 코덱·바인딩·버퍼 전송도 직접 소유 | 프로파일 결과 CPU 커널의 이득이 명확한 경우 |

UI 라이브러리의 React/Svelte/기본 DOM 선택보다 픽셀 소유권, 변경 영역, Worker 통신 설계가 그리기 성능에 더 큰 영향을 줄 가능성이 높다. 이는 현 코드의 작업 경로에서 도출한 설계 판단이며 신규 비교 실측값은 아니다.

브러시 포인트마다 UI 컴포넌트 전체나 레이어 배열을 새 상태로 갱신하는 구조는 피한다. UI 상태에는 도구·슬라이더·선택 레이어 같은 작은 값만 두고 이미지와 이력은 엔진이 소유한다.

## 3. 현재 성능 기준과 해석

[실측 자료](evidence/qt-exit-baseline.json)에 로컬 산출물과 3회 순차 실행의 원본 값을 남겼다.

### 산출물

- 현재 로컬 `retropaint.wasm`: 20,002,847바이트, 약 19.08 MiB.
- bundle의 파일 합계: 21,367,748바이트, 약 20.38 MiB. 홈페이지 wrapper/manifest가 포함된 폴더 총합과는 다르다.
- Wasm에는 앱·정적 Qt 코드·한글 글꼴 등이 포함된다. 전부를 ‘Qt 자체 용량’으로 계산할 수 없다. 현재 글꼴 원본만 약 1.96 MiB다.
- Wasm을 로컬 gzip level 6으로 압축한 참고 크기는 약 6.71 MiB다. 이는 실제 Pages HTTP 전송 크기나 cold start 시간이 아니다.

Qt를 제거한 작고 필요한 구성은 용량 감소 여지가 크지만, 이미지 코덱·글꼴·UI·Wasm 엔진을 어떻게 포함하는지에 따라 달라진다. 새 제품을 빌드하기 전에 ‘몇 KB’ 또는 ‘몇 배 빠름’을 약속할 근거는 없다. [Qt 문서](https://doc.qt.io/qt-6/wasm.html)도 Wasm에 앱과 Qt 코드가 정적으로 링크되는 구조를 설명한다.

### 네이티브 코어 재측정

macOS 27 ARM64 / Qt 6.12.0, 기존 `perf_probe`의 세 번 실행 중앙값이다.

| 작업 | 1920×1080 | 4096×4096 |
| --- | ---: | ---: |
| 직선 그리기+commit 20회 합계 | 17ms | 95ms |
| Undo/Redo 40회 합계 | 7ms | 67ms |
| 채우기 | 3ms | 25ms |
| 프로젝트 저장 | 62ms | 448ms |
| 프로젝트 열기 | 5ms | 33ms |

이 probe는 QPainter 직선과 Document 연산을 측정한다. 새 smooth brush, 실제 펜 입력 지연, UI 화면 표시, 모바일 성능이나 저장 중 UI 정지 시간은 아니다. 네이티브 앱의 저장은 이미 별도 작업 경로를 사용한다. 위 수치로 FPS나 체감 지연을 계산하면 안 된다.

기존 [웹 코어 측정](evidence/web-performance.json)에서는 2048² 채우기 28~31ms, 약 3MP 두 레이어의 프로젝트 인코딩 187~191ms, PNG 인코딩 104~110ms였다. 이전 동일 데스크톱 환경에서의 코어 시험이며 모바일 펜 시험은 아니다. 웹에서는 이런 작업의 UI 스레드 점유를 줄이는 여지가 있다.

## 4. 다시 짤 때 좋아질 수 있는 부분

- Qt Widgets·플랫폼 창 계층 없이 DOM 레이아웃으로 화면 폭과 키보드에 맞출 수 있다.
- CSS 토큰과 일반 HTML 제어로 Studio/Win98 스킨, 큰 터치 표적, 초점·접근성 이름을 구성하기 쉬워진다. 캔버스 자체의 접근성이 자동 해결되는 것은 아니다.
- DOM Pointer Events의 펜/터치 소유권·입력 샘플을 앱에서 직접 관리할 수 있다. 필압·팜 리젝션 품질은 장치/OS/브라우저 영향이 남는다.
- 파일·IndexedDB 데이터가 JS와 Wasm 힙을 오가던 복사를 일부 줄일 수 있다. 새 Worker 구조의 전송 방식이 잘못되면 이득이 사라진다.
- Qt SDK 빌드와 현재 고정 Emscripten 조합의 운영 부담을 줄일 수 있다. Qt-free Wasm을 쓰면 해당 컴파일러/라이브러리 관리 비용은 남는다.

이점 중 UI 구성 자유도는 구조적으로 기대할 수 있다. 첫 로딩·메모리·획 처리 속도의 실제 개선량은 별도 PoC로 검증해야 한다.

## 5. 성능이 나빠질 수 있는 핵심 경로

### 전체 픽셀 복사와 Undo

현재 QImage는 공유 복사 후 쓰기 때 분리되며, 획 commit은 변경 사각형을 찾기 위해 바뀐 레이어 전체를 스캔한다. Qt를 없애도 같은 알고리즘을 옮기면 비용은 남는다. JS에서 매번 `slice()`로 전체 레이어를 복제하면 더 불리할 수 있다.

RGBA8 기준 2048² 한 장은 16 MiB, 4096² 한 장은 64 MiB다. 4 Mi 픽셀 전체를 초당 120번 복사하면 복사 한 경로만 약 1.875 GiB/s다. 이는 이론적인 데이터량이지 현재 앱의 측정 대역폭이 아니다.

새 엔진은 변경 사각형/타일과 한 획의 원본 패치를 소유하고 이력 예산을 제한해야 한다. PNG 문자열이나 전체 DataURL을 매 획 이력으로 남기지 않는다. 기존의 단일 revision·Redo 분기·저장 상태 계약을 유지한다.

### 브러시와 합성

현재 브러시는 간격 보간 뒤 픽셀별 거리·경도·알파를 계산한다. 큰 브러시와 긴 이동은 어느 언어에서도 처리 픽셀이 증가한다. 같은 코드를 JS 픽셀 루프로 옮기면 C++/Wasm보다 느려질 가능성이 있다. Canvas의 `stroke()`만 사용하면 간단하고 빠를 수 있으나 현재 ‘한 획 내 최대 coverage’와 불투명도·부드러운 지우개 의미가 달라질 수 있다.

작품 픽셀은 엔진이 소유하고 Canvas는 표시 수단으로 사용하는 구성을 우선 검증한다. 고급 GPU 합성은 큰 문서에서 이점이 있을 수 있지만 texture 메모리, 읽기 회수, 손실 복구·정확성 비용도 있다. 초기부터 모든 경로를 WebGPU 전용으로 묶지 않는다.

### UI 스레드와 Worker

한 프레임의 총 예산은 60Hz에서 약 16.7ms, 120Hz에서 약 8.3ms다. 이 안에는 앱 외 작업도 포함된다. 긴 채우기·인코딩을 UI 스레드에서 실행하면 DOM UI여도 멈춘다.

[OffscreenCanvas/Worker](https://web.dev/articles/offscreen-canvas)는 선택지다. Worker가 항상 더 낮은 획 지연을 보장하는 것은 아니며 메시지 대기와 경쟁 작업이 추가된다. 포인트를 묶어서 보내고 순서·획 끝점·취소를 보존한다. 전체 레이어는 매 포인트마다 보내지 않는다. 기능과 컨텍스트 생성 가능 여부를 검사하고 fallback을 둔다.

현재 공개 Pages 응답에는 COOP/COEP가 없었다. [Emscripten pthreads](https://emscripten.org/docs/porting/pthreads.html)는 격리 헤더를 요구하므로 SharedArrayBuffer를 전제한 설계는 현재 배포에 바로 적용할 수 없다. 일반 Worker+소유권 이전, Worker 안의 단일 스레드 Wasm, OffscreenCanvas는 pthreads와 구분한다. Qt가 없는 새 엔진도 반드시 멀티스레드 Wasm일 필요는 없다.

### 픽셀 읽기·DPR·메모리

`getImageData`/GPU readback을 매 이동마다 실행하지 않는다. 브라우저 구현에 따라 GPU/CPU 동기화 비용이 크며 [Chrome 문서](https://developer.chrome.com/blog/canvas2d/)도 readback 비용을 설명한다. `willReadFrequently`는 읽기 중심 버퍼에서 검토하고 모든 canvas에 일괄 지정하지 않는다.

화면 버퍼의 픽셀 수는 논리 폭×높이×DPR²로 늘어난다. DPR 3은 한 축 3배·픽셀 9배다. 문서 데이터까지 화면 DPR로 키우면 안 된다. 레이어·작업 사본·합성·Undo·인코딩 버퍼의 합계와 GC 피크를 관리한다.

현재 Wasm의 초기 힙 64MB·최대 512MB는 전체 브라우저 메모리나 RSS와 같지 않다. JS로 바꾼다고 메모리 제한 문제가 사라지는 것도 아니다.

## 6. 기존 결과와 데이터 호환성

Qt의 ARGB32 premultiplied와 ImageData의 일반적인 RGBA 배열은 같은 바이트 표현이 아니다. little-endian의 채널 배치·알파 premultiply/unpremultiply·반올림을 검증해야 한다. [HTML 표준](https://html.spec.whatwg.org/multipage/canvas.html#premultiplied-alpha-and-the-2d-rendering-context)도 알파 표현 변환의 정확도 손실을 명시한다.

다음 항목이 전환의 높은 위험 범위다.

- 기존 RPAINT01의 little-endian 정수, UTF-8 이름, visible, PNG 길이·후행 데이터 검증과 자원 한도. PNG 압축 바이트의 동일성은 기존 계약이 아니지만 디코딩한 문서 픽셀은 보존해야 한다.
- 브라우저 canvas에 모든 문서 픽셀을 통과시키면 반투명 픽셀의 반올림 차이가 생길 수 있다. 기존 레이어를 정확히 보존할 필요가 있으면 별도 권위 픽셀 버퍼와 검증된 PNG 경로를 유지한다.
- 도형 AA·선 끝·보간과 새 문자 래스터화는 Qt 결과와 다를 수 있다. 이미 `.rpaint`에 확정된 문자는 픽셀이므로 재조판할 필요가 없다. 새 문자/획의 차이는 비교 이미지로 정의한다.
- 이미지가 디코딩되기 전에 크기·길이를 제한한다. File.size 검사만으로 압축 폭탄을 막을 수 없다. PNG/JPEG/BMP/GIF의 현재 허용 범위·JPEG 방향·GIF 첫 프레임 동작을 확인한다.
- ‘투명 배경’은 기존 흰 픽셀 자동 삭제와 다르다. [앞선 알파 시험](evidence/ui-planning-alpha-export.json)의 JPG/BMP 바탕색 문제도 새 엔진에서 다시 발생할 수 있다.
- 저장/취소/권한 거절/비동기 늦은 완료가 문서와 Redo를 바꾸지 않아야 한다. 요청에 문서 세대·revision을 묶는 현재 의미를 보존한다.

TypeScript 또는 Rust라는 언어 선택만으로 이 호환성이 자동 확보되지 않는다.

## 7. 데스크톱 버전의 영향

| 방식 | 영향과 판단 |
| --- | --- |
| 웹/PWA 중심 | GitHub Pages와 동일 UI를 사용하기 쉬움. 설치/오프라인은 별도 캐시·갱신 설계 필요. 브라우저 파일 권한과 다운로드의 한계는 남음 |
| Tauri | OS WebView 사용. 런타임 중복 배포를 줄일 수 있으나 운영체제별 WebView·펜·Canvas 차이 검증 필요 |
| Electron | Chromium/Node 기반의 다중 프로세스 구조. 렌더러 버전을 통제하기 좋지만 크기·기본 메모리를 줄이기 위한 기본 선택으로 보기는 어려움 |
| 별도 네이티브 UI/엔진 | 큰 문서·네이티브 제어를 유지할 수 있으나 웹과 UI/입력 경로를 따로 관리하는 비용이 큼 |

[Tauri WebView 문서](https://v2.tauri.app/reference/webview-versions/)와 [Electron 프로세스 모델](https://www.electronjs.org/docs/latest/tutorial/process-model)을 기준으로 한 구조 비교다. 이 앱을 두 셸로 빌드한 크기·RSS·획 지연 비교는 아직 없다. ‘Tauri가 무조건 더 빠르다/가볍다’고 단정하지 않는다.

Tauri를 선택해도 매 포인터 이벤트를 Rust로 왕복시키거나 전체 이미지를 JSON으로 전송하지 않는다. 문서 엔진을 WebView 내부 Worker/Wasm에서 실행하고 네이티브 쪽은 파일·앱 수명 같은 경계를 맡는 구성을 먼저 검토한다. 네이티브 연산이 필요하면 묶음 명령과 [raw binary IPC](https://v2.tauri.app/develop/calling-rust/)를 활용할 수 있지만 IPC 비용이 0이라는 뜻은 아니다.

현재 네이티브 앱은 QSaveFile의 안전한 파일 교체, 로컬 복구와 잠금을 갖는다. 새 파일 API의 직접 덮어쓰기를 동등한 대체로 취급하지 않는다. OS별 실패·취소·잠금 상황을 확인하고, 새 앱 식별자/저장 위치로 바뀔 때 이전 복구 파일의 인계 경로를 제공해야 한다.

저장소 AGENTS의 현재 네이티브 ‘browser embedding 금지’ 규칙은 WebView 셸을 택하면 로컬 앱 자산 전용으로 적용 범위를 명시하는 아키텍처 결정이 필요하다. 이번 검토에서는 규칙을 변경하거나 셸을 설치하지 않았다.

## 8. GitHub Pages·저장소 관리

같은 `/mypaint/` 정적 배포 방식은 유지 가능하다. 기본 전제는 서버 렌더링이 없는 정적 빌드, 상대 자산 경로, 같은 사이트 자산, 앱 전용 저장소 이름이다. 특정 UI 프레임워크의 서버 기능은 배포 전제로 두지 않는다.

현재 `tools/stage_web.py`는 `retropaint.wasm/js`, `qtloader.js`와 고정 파일 구성을 요구한다. 새 JS/hashed chunk 구조에 맞게 소유 manifest와 검증 규칙을 이행해야 한다. 오래된 Qt manifest와 수동 변경 보호를 읽을 수 있어야 하며 파일 검증·일시 폴더·교체 실패 복원·prune 의미는 유지한다.

같은 origin이면 현재 IndexedDB `retropaint-local-v1`의 이전 복구 Blob을 읽는 이행 경로를 만들 수 있다. 기존 탭과 새 버전의 동시 실행, 새 형식과 스키마, worker 늦은 완료를 확인한다. 저장소를 먼저 지우는 마이그레이션은 피한다. 네이티브 WebView와 공개 웹은 저장소가 자동 공유되지 않는다.

Service Worker를 추가한다면 오래된 UI/새 엔진 자산 혼합과 미저장 문서가 있는 탭의 갱신 문제를 별도 다룬다. 초기 전환에서 무조건 도입하지 않는다. 기존 원격 `origin`과 별도 홈페이지 폴더의 수동 commit/push 방식은 유지할 수 있다.

## 9. 권장 검증 순서와 전환 조건

1. 기존 앱의 파일·Undo·취소·알파·레이어 결과를 기준 fixture로 고정한다. 기존 앱과 배포를 보존한다.
2. 별도 Qt-free PoC에서 브러시/지우개·레이어·Undo/Redo·PNG·RPAINT01 열기/저장만 연결한다. 모바일 UI만 보이는 데모를 편집 엔진 검증으로 대신하지 않는다.
3. 같은 점·필압 입력과 문서로 800×600, 2048², 웹 한도 문서, 네이티브 대형 문서를 비교한다. 4Mi 픽셀 문서의 레이어 수는 현 합계 한도를 지킨다. 기존 웹 한도에서 4096²는 허용되지 않으므로 네이티브 전용 시험과 섞지 않는다.
4. 초기 전송/엔진 준비 시간, 포인터 처리 p50/p95/p99, 화면 표시 지연, 긴 프레임, 획 종료 commit, 채우기, 저장/복구, 피크 메모리를 따로 기록한다. 실제 iPad/Android와 데스크톱을 포함한다.
5. 데이터 복사·readback·전체 스캔이 병목이면 먼저 줄인다. 여전히 CPU 커널이 지배하면 Qt-free Wasm을 비교한다. 언어를 먼저 정하고 성능 이득을 가정하지 않는다.
6. 파일/예외 계약과 실제 장치 성능이 충족된 뒤 도형·선택·문자·변형을 이식한다. 이후 데스크톱 셸과 배포 도구를 확정한다.
7. 기존 문서/복구 파일을 여는 경로와 되돌아갈 수 있는 기존 릴리스를 확보한 뒤 새 버전을 기본으로 전환한다.

새 구조의 성공 기준은 보기 좋은 스킨만이 아니다. 같은 사용자의 그림과 입력을 안전하게 유지하면서 목표 장치에서 초기 로딩·편집 응답·메모리 중 실제 개선을 보여야 한다. 개선폭과 허용할 렌더링 차이는 PoC 결과로 정한다.

## 검토 결론과 남은 불확실성

웹·모바일·스킨을 중심으로 장기 확장하려면 Qt-free 웹 UI는 유력한 선택이다. 현재 C++ 구현의 기능을 그대로 버리면 호환·복구·성능 검증 자산도 잃으므로 단계적 대체가 적절하다. 완전 제거의 비용은 높고, 큰 브러시/큰 문서/네이티브 저장에서 성능 퇴보가 발생할 수 있다.

이번에는 기존 코드·파일·실측 기준과 플랫폼 제약을 확인했다. Qt-free 새 엔진, Tauri/Electron 앱, 실제 모바일 비교는 구현·측정하지 않았다. 제품 코드·배포 산출물·Git 리모트·commit·push는 변경하지 않았다.
