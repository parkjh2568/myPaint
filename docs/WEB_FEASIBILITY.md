# 웹 버전과 GitHub Pages 배포 검토

검토일: 2026-11-03. 현재 작업 트리의 CMake, 제품 소스, 저장 형식, 아키텍처, 테스트·CI와 Git 리모트를 확인했다. 이 문서는 구현·배포 제안이며 웹 실행 검증 결과가 아니다.

후속 [웹 구현 작업계획](WEB_IMPLEMENTATION_PLAN.md)은 파일·함수별 변경, 비동기 수명·복구 순서, 회귀 시험, 게시 도구의 완료 조건을 정의한다.

## 1. 판정

**구현 가능하다. Qt WebAssembly 이식시험 → 브라우저 기능 구현 → 기존 홈페이지의 mypaint 폴더에 산출물 반영 순서로 진행한다.** 두 저장소는 각 폴더의 origin만 사용하고 홈페이지 커밋·push는 별도로 수행한다.

기존 홈페이지는 형제 폴더 `/Users/jhpark/code/myService/parkjh2568.github.io`에서 관리한다. myPaint의 mypage 리모트는 제거했고 추가 배포 체크아웃을 만들지 않는다. 웹 빌드는 완성된 결과만 이 홈페이지의 mypaint 하위에 반영하며 Git staging·동기화·커밋·push는 실행하지 않는다. [두 폴더 Git 관리](GIT_WORKFLOW.md)

GitHub Pages는 정적 웹 호스팅이므로 브라우저에서 실행하는 HTML·JavaScript·WebAssembly를 배포하는 방식이 맞는다. 그림 편집과 파일 처리를 방문자의 기기 안에서 수행하도록 설계하면 별도 애플리케이션 서버가 필요하지 않다. 네이티브 실행 파일을 올리는 것만으로 웹 앱이 되지는 않는다. [GitHub Pages 설명](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

기존 코드의 재사용 가능성과 현재 상태 그대로의 빌드 가능성은 구분해야 한다. 특히 예외, 중첩 이벤트 루프, 스레드, 저장 완료 판정은 선행 해결 항목이다. 전체 이식 비용·다운로드 크기·모바일 지원 범위는 이식시험 전에는 확정하지 않는다.

## 4. 이식 전에 해소할 기술 제약

### Qt SDK·예외·이벤트 루프

검토한 Qt 6.12 문서는 기본 Wasm 배포판의 예외 미지원을 명시한다. 현재 Document의 검증 실패와 할당 실패 처리는 예외에 의존한다. 앱에 컴파일 옵션 하나만 추가하는 것으로 기본 Qt 바이너리의 제약이 해결된다고 보아서는 안 된다.

예외를 유지하는 첫 시험은 소스 빌드한 Qt의 `-feature-wasm-exceptions`와 컴파일·링크의 `-fwasm-exceptions` 조합이다. 이 구성에서는 `QApplication::exec()`를 호출하지 않고 앱·창의 수명을 유지하며 main이 반환하는 웹 진입점이 필요하다. 기본 Wasm의 `QDialog::exec()` 등 중첩 루프도 대체해야 한다. Asyncify/JSPI를 기존 코드 전체의 자동 해결책으로 채택하지 않는다. 문서상 이벤트 루프 요구와 지원 브라우저 차이를 별도 검증해야 한다. [Qt WebAssembly: 예외·시작·이벤트 루프](https://doc.qt.io/qt-6/wasm.html#wasm-exceptions)

현재 문서의 Qt 6.12.0 대응 Emscripten은 5.0.5다. 실제 선정 버전의 호스트 Qt·Wasm Qt·Emscripten을 함께 고정한다. `qt_add_executable`을 사용한 HTML·로더 생성도 필요하다. 기존 네이티브 최소 버전·CI를 웹 버전에 맞춰 일괄 변경할 필요는 없다. [Qt WebAssembly 빌드](https://doc.qt.io/qt-6/wasm.html)

**통과 조건:** 작은 Widgets 앱에서 정상 시작, 클릭 콜백의 의도적인 검증 예외 처리, 오류 후 계속 그리기, 한글 표시, 비동기 대화상자가 실제 브라우저에서 동작해야 한다. 실패하면 SDK 선택을 다시 평가한 뒤 전체 이식 여부를 결정한다.

### 스레드와 Pages 응답 헤더

멀티스레드 Qt Wasm은 SharedArrayBuffer와 cross-origin isolation이 필요하다. GitHub Pages의 사용자 지정 헤더는 공식 커뮤니티 답변에서 미지원으로 안내됐으며, 해당 답변은 2023년이고 2026년에도 요청이 이어진다. 이번에 대상 사이트의 실제 헤더를 측정하지 않았으므로 COOP/COEP를 직접 설정할 수 있다는 전제를 두지 않는다. 따라서 **최초 지원 경로는 단일 스레드**로 제안한다. [Qt 스레드 조건](https://doc.qt.io/qt-6/wasm.html#multithreading), [GitHub 헤더 지원 논의와 운영 측 답변](https://github.com/orgs/community/discussions/54257)

현재 `Canvas::fillAt`, `MainWindow::stageFile`, 자동 복구의 `std::async`를 그대로 둘 수 없다. 브라우저 주 스레드의 동기 대기는 응답 정지와 교착 위험도 있다. [Emscripten 스레드·주 스레드 대기](https://emscripten.org/docs/porting/pthreads.html#blocking-on-the-main-browser-thread)

대안은 작업 특성에 따라 결정한다. 채우기처럼 루프를 소유한 연산은 일정량씩 처리하고 이벤트 루프에 반환할 수 있다. QImage PNG 인코딩은 호출 자체가 동기식이므로 타이머에 넣는 것만으로 응답성이 확보되지 않는다. 첫 버전은 작은 문서 한도로 측정하고, 기준 미달이면 독립 Worker/별도 Wasm 모듈의 메시지 전달 구조나 인코딩 경로를 추가 검토한다. Worker는 복사 비용·메모리·취소·오래된 결과 폐기까지 확인해야 하며, 단순한 스레드 치환으로 취급하지 않는다.

Service Worker를 이용한 격리 우회는 최초 지원 경로에서 제외한다. 도입 시에는 첫 로드·재로딩·캐시·기존 홈페이지 Service Worker와의 간섭을 별도 검증한다.

## 6. 저장·복구·실패 계약

### 파일 열기

Qt의 `getOpenFileContent`는 비동기로 선택 파일 전체를 메모리에 읽어 콜백에 전달한다. 기존 경로 기반 열기와 호출 규약이 다르다. 웹의 큰 파일은 JS File.size를 **읽기 전에** 검사하는 입력 경계를 두는 것이 안전하다. 콜백에서만 크기를 검사하면 읽기 버퍼 할당은 이미 일어난 뒤다. [Qt 파일 내용 열기](https://doc.qt.io/qt-6/qfiledialog.html#getOpenFileContent)

이미지 치수, 누적 디코딩 픽셀, 레이어 수, 레코드 길이, UTF-8 검증은 기존 규칙을 유지한다. 브라우저용 작업 한도를 넘는 파일은 명확한 이유와 함께 거부하고 기존 문서·pending·Redo는 보존한다. 열기 요청 후 다른 문서로 전환되었으면 오래된 콜백이 새 문서를 덮어쓰지 않도록 요청 소유권을 확인한다.

### 다운로드와 복구

`saveFileContent`는 비동기 반환이며 파일 쓰기 성공을 반환하는 API가 아니다. 이 반환 시점에 네이티브의 `QSaveFile::commit` 성공과 같은 의미를 부여할 수 없다. [Qt 파일 내용 저장](https://doc.qt.io/qt-6/qfiledialog.html#saveFileContent)

| 사용자 동작 | 확인할 수 있는 경계 | 제안하는 UI·상태 |
| --- | --- | --- |
| 프로젝트 다운로드 | 후보 인코딩과 다운로드 요청 | “다운로드 요청됨”. 파일 저장 완료 표시·무조건 `markSaved()` 금지 |
| PNG/JPEG 내보내기 | 미리보기 인코딩과 다운로드 요청 | 기존처럼 문서·pending·프로젝트 저장 상태를 바꾸지 않음 |
| 브라우저 복구 사본 | 해당 snapshot의 영속 저장 완료 콜백 | “이 브라우저에 복구 사본 저장됨”, 시각·revision 표시. 외부 파일 저장과 구분 |
| 실패·취소 | 해당 작업만 중단 | 문서·이력·미확정 편집·직전 정상 복구 사본 유지 |
| 탭 종료·새로고침 | 종료 시점의 비동기 저장 완료 보장 없음 | 작업 중 주기적 복구, 편집 손실 위험 안내. 종료 이벤트에만 저장을 의존하지 않음 |

웹의 프로젝트 다운로드도 처음에는 기존 내보내기처럼 후보를 인코딩하고 pending을 보존하는 쪽을 권장한다. 파일 다운로드만으로 pending을 확정하거나 saved revision을 바꾸지 않는다. 필요하면 “편집 확정”을 명시적으로 제공한다. 비동기 작업 중 편집 허용 범위를 먼저 정하고, 완료 시 문서 revision뿐 아니라 pending/요청의 소유권도 검증해야 한다.

브라우저 가상 파일의 QSaveFile 교체는 OS 파일 다운로드 완료나 IndexedDB 영속화와 동일하지 않다. MEMFS는 기본 메모리 파일시스템이고, IDBFS의 영속 반영은 `syncfs` 완료·오류 처리까지 필요하다. [Emscripten 파일시스템](https://emscripten.org/docs/api_reference/Filesystem-API.html)

복구는 새 snapshot을 별도 키에 저장한 뒤 성공한 버전을 선택하는 방식 등을 검토하여 실패가 이전 정상 사본을 지우지 않게 한다. 확정된 문서만 복구하는 첫 범위라면 미확정 문자·선택은 포함되지 않는다는 기존 제한도 표시한다. 저장소 사용 불가·용량 부족이면 자동 복구를 보장하지 말고 프로젝트 다운로드를 안내한다.

여러 `github.io` 하위 경로는 같은 origin을 공유할 수 있으므로 앱·문서·스키마별 저장 키를 사용한다. 경로 이름은 보안 격리가 아니다. 탭별 메모리 파일 잠금을 공유 잠금으로 착각하지 말고, 초기에는 탭별 복구 사본과 충돌 안내로 덮어쓰기를 피한다. 사이트 데이터 삭제·비공개 모드·다중 탭·브라우저 강제 종료도 시험한다.

## 7. 자원 한도와 UI/UX

현재 네이티브 한도는 이미지 32M 픽셀, 문서 합계 64M 픽셀, 16레이어, 입력 300MiB이며 이력 기본 예산은 256MiB다. 픽셀 원본 외에 후보 이미지, 합성, 히스토리, PNG, JS 전달 버퍼, 다운로드 Blob이 겹치므로 이 숫자를 웹에 그대로 적용하면 위험하다. 해상도·레이어·입력 바이트·이력·동시 인코딩을 함께 제한하는 웹 프로필을 두고 실제 브라우저 메모리·응답성으로 값을 정한다. 첫 버전에서 한도를 초과하는 네이티브 프로젝트를 지원한다고 약속하지 않는다.

웹에 맞는 UI는 다음과 같다.

- 초기 화면에 “기기 안에서 편집”, 지원 파일·한도, 파일 열기를 제공한다. 사용자 그림 업로드 기능은 넣지 않는다.
- 그림판 아이콘·Undo/Redo는 유지하고 좁은 화면에서 레이어·옵션을 접을 수 있게 한다. 아이콘에 툴팁·접근성 이름을 제공한다.
- “프로젝트 다운로드”, “이미지 내보내기”, “브라우저 복구”를 구분한다. 복구 실패를 영구 저장 성공처럼 표시하지 않는다.
- 클립보드 권한 거부에는 파일 열기·이미지 다운로드 대안을 제공한다. 브라우저 단축키는 편집 영역의 포커스와 실제 지원 여부에 맞춰 처리한다.
- 긴 변환은 진행·취소 상태를 표시한다. 취소 후 도착한 결과는 폐기한다. UI만 비동기처럼 보이고 주 스레드는 오래 점유하는 구현을 피한다.
- 한글 글꼴은 사용 가능한 글꼴과 실제 배포 라이선스를 확인한다. 데스크톱 시스템 글꼴 목록과 같은 선택을 보장하지 않는다.
- 로딩 실패에 빈 화면 대신 재시도·지원 환경 안내를 표시한다. WebGL 컨텍스트 손실·탭 중단 후에는 정상 복구 경로를 제공한다.

## 8. 두 폴더와 로컬 산출물 반영

```text
myService/myPaint ── 소스 commit·push ──> 해당 origin
        │
        └─ Wasm 빌드 → 검증된 dist/web/
                            │ mypaint/만 반영, Git 상태 보존
                            v
myService/parkjh2568.github.io/mypaint/
        └─ 홈페이지 폴더에서 수동 commit·push → 해당 origin → Pages
```

목표 URL은 `https://parkjh2568.github.io/mypaint/`다. 로컬 홈페이지 workflow는 main push·root 전체 게시를 정의한다. 이 설정이 유지되면 mypaint 폴더와 기존 페이지가 함께 게시된다. 실제 사이트 설정·push 권한·성공 여부는 홈페이지 작업에서 확인한다.

웹 빌드는 홈페이지의 index·css·js·img·workflow를 바꾸지 않는다. 산출물은 먼저 소스 저장소 안에서 완성·검증한 후 앱 폴더만 갱신한다. 대상의 수동 수정·staged 변경·심볼릭 링크·출처 불명 파일·경로 탈출을 검사하고, 실패하면 기존 정상 결과를 보존한다. 다른 홈페이지 변경 때문에 전체 작업 트리를 강제로 clean하게 만들거나 staging을 초기화하지 않는다.

자동 fetch·pull·add·commit·push와 인증 설정 변경은 구현 범위에서 제외한다. 홈페이지 최신화는 빌드 결과 반영 전에 사용자가 해당 폴더에서 수행한다. 반영 뒤 staged diff 전체를 검토하여 기존 staged 변경이 의도치 않게 커밋에 포함되지 않도록 한다.

HTML·CSS·JS·Wasm·사용하는 로컬 자산·고지·manifest만 포함한다. SDK·네이티브 앱·소스맵·secret·사용자 파일은 제외한다. manifest에는 식별 가능한 소스 상태·툴체인·산출물 해시를 기록한다. 자산 버전·하위 경로·캐시는 실제 URL에서도 검증한다.

Pages는 사이트 artifact를 게시하므로 앱만 담은 별도 artifact가 기존 홈페이지에 부분 병합될 것으로 가정하지 않는다. 현재 root 게시 흐름을 유지한다. [Pages Actions workflow](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

## 9. 오프라인 규칙·배포 고지

현재 AGENTS.md의 네트워크·원격 리소스·웹뷰 금지는 데스크톱에서 유지한다. 웹 구현 시에는 사용자가 요청한 정적 웹 게시에 필요한 **동일 사이트 앱 자산 로딩**을 웹 대상에 한해 문서화해야 한다. 그림 업로드, 계정, 텔레메트리, 외부 CDN·웹폰트, 원격 이미지 가져오기, 셸 실행·브라우저 임베딩을 추가하는 근거로 확대하지 않는다. 이번 검토에서는 AGENTS.md를 바꾸지 않았다.

“사용자 그림을 업로드하지 않는다”와 “웹 접속에 네트워크가 전혀 없다”는 다른 주장이다. 웹 파일을 처음 받는 요청은 발생한다. 필요하면 접속 기록 등 호스팅 제공자의 동작도 앱 자체의 데이터 수집과 구분하여 설명한다.

현재 NOTICE.md는 동적 링크 네이티브 Qt를 설명한다. Wasm 기본 정적 링크로 배포한다면 정확한 Qt 빌드·플러그인·폰트·이미지 코덱의 라이선스와 소스 제공·수정/재링크 요건을 다시 확인하고 웹 배포 고지를 작성해야 한다. 앱 소스가 MIT라는 사실만으로 의존성 배포 요건이 없어지지 않는다. [Qt 라이선스 안내](https://doc.qt.io/qt-6/licensing.html)

## 10. 단계별 실행 계획과 완료 기준

| 단계 | 작업 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 0. 기준 고정 | 현재 개선분의 검증·커밋 기준, 대상 Pages 저장소·게시 방식 확인 | source revision과 게시 위치를 명확히 식별 |
| 1. 이식시험 | 단일 스레드·예외 지원 Qt, 웹 main·비동기 오류창, 최소 캔버스와 한글 표시 | 실제 브라우저에서 그리기→Undo/Redo→의도적 예외→계속 편집. 코덱·크기·응답성 측정 |
| 2. 편집 기능 | 도구·선택·문자·레이어 재사용, 동기 대화상자·채우기 대기 제거 | 핵심 동작이 네이티브와 일치, 취소·포커스 상실·IME 검증 |
| 3. 파일과 복구 | 제한된 바이트 입출력, `.rpaint` 왕복, 이미지 다운로드, 영속 복구 | 손상 파일·용량 부족·취소·오래된 완료 결과에서도 현재 문서와 직전 사본 보존 |
| 4. 웹 UX·자원 | 화면 대응, 저장 상태 문구, 한도와 긴 작업·로딩 실패 처리 | 지원 브라우저별 메모리·지연·클립보드·키보드 확인, 모바일 범위 별도 명시 |
| 5. 산출물 반영 | 기존 홈페이지 mypaint 폴더만 갱신, Git 쓰기 명령 제외 | 다른 홈페이지 파일·staging 불변, 실패 시 정상 산출물 보존 |
| 6. 실호스팅 확인 | 정확한 Pages 하위 경로와 캐시 상태에서 시험 | 새 방문·재방문·직접 접속·이전 캐시·복구가 실제 URL에서 통과 |

브라우저 시험은 Chromium·Firefox·Safari의 명시한 버전에서 수행한다. Safari/iOS, 터치, 한글 IME, 이미지 클립보드 지원을 데스크톱 offscreen 결과로 대체하지 않는다. 단일 스레드 Pages 환경 그대로 시험하여 로컬 COOP/COEP 개발 서버에서만 우연히 통과하는 구성을 피한다.

필수 실패 시나리오는 잘린/위조 프로젝트, 크기 초과 파일의 읽기 전 거부, PNG 디코딩 실패, 저장소 거부·용량 부족, 다운로드 취소, 작업 중 다른 문서 열기, 다중 탭, 강제 새로고침, 캐시 버전 불일치, WebGL 손실이다. 다운로드 취소를 API로 관찰할 수 없는 경로는 그 한계를 UI 상태로 반영하고 성공으로 판정하지 않는다.

공유 코어 수정 후 기존 CTest를 실행하고 네이티브 UI 변경 후 offscreen smoke를 유지한다. 여기에 브라우저 실동작 시험을 추가한다. Wasm에서 테스트 실행 파일을 생성했다는 이유만으로 브라우저 테스트가 통과한 것으로 기록하지 않는다.

권고는 **기존 Qt 코드를 최대한 유지하는 작은 이식시험부터 시작**하는 것이다. 예외·이벤트 루프·단일 스레드 성능이 통과하면 파일·복구 계약을 이식하고, 그 뒤 기존 홈페이지의 `/mypaint/`에 웹 결과물을 반영한다. 실제 게시는 홈페이지 폴더의 수동 커밋·push로 수행한다. 게시 브랜치·빌드 방식·기존 홈페이지 구조와 접근 권한은 실제 게시 구현 전에 확인한다.
