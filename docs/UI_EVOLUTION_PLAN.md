# 투명 배경·반응형 UI·스킨·아이콘 개선 계획

2026-11-04 / 분석·설계 단계. 웹과 데스크톱 공통 적용을 기준으로 한다. 현재 작업 트리의 Studio UI와 로컬 `dist/web`를 조사했으며, 이 문서는 구현 완료 보고가 아니다. 이번 요청에서는 제품 코드·배포 산출물을 변경하지 않았다.

## 1. 권고안

현재 Qt 편집 엔진을 유지하고, 문서 투명도·화면 배치·스킨·입력 설정을 각각의 소유 상태로 분리한다. 먼저 투명 문서의 저장 안전성과 터치 입력 취소를 검증하고, 공통 표시 토큰과 아이콘을 정리한 뒤 반응형 패널을 적용한다. 스킨은 `Studio Dark`와 `Classic 98` 두 개로 시작한다. 화면 크기와 입력 밀도는 어느 스킨에서도 독립적으로 적용한다.

핵심 판단은 다음과 같다.

- 투명 픽셀·PNG·프로젝트 형식의 기반은 이미 있다. 새 파일 형식을 만들기 전에 기존 알파 채널을 활용할 수 있다.
- `background`가 보조색·단일 레이어 지우기 색·확장 색·불투명 내보내기 바탕색을 겸한다. 투명도 UI보다 이 의미의 경계와 기존 계약을 먼저 확정해야 한다.
- 모바일에서는 오른쪽 패널을 접고 도구를 재배치해야 한다. 웹 CSS만으로 Qt 안의 도구와 대화상자는 재배치되지 않는다.
- 기기 이름보다 사용 가능한 창 크기와 입력 능력을 사용한다. 태블릿의 분할 화면과 터치 노트북을 함께 다룬다.
- Win98 느낌은 색·직각 테두리·입체 버튼·직접 제작한 아이콘으로 제공한다. 같은 문서와 QAction, 입력 경로를 사용한다.

### 투명도 내보내기 재현

기존 네이티브 paintcore와 Qt 6.12를 연결한 독립 probe로 확인했다. 코드 변경 없이 흰 배경/투명 배경과 반투명 빨강 픽셀을 PNG·JPG·BMP로 인코딩해 다시 읽었다.

- 투명 background의 PNG 빈 픽셀은 `(0,0,0,0)`, 반투명 빨강은 `(255,0,0,128)`을 유지했다.
- 같은 문서의 BMP 빈 픽셀은 `(0,0,0,255)`였다. JPG도 빈 영역이 검정이었다. 바탕색을 확정하지 않은 RGB 변환이 사용자 기대와 다르다.
- RPAINT01 재직렬화에서 투명 background와 레이어 픽셀은 정확히 일치했다.
- PNG를 이미지로 다시 열면 현재 코드가 문서 background를 흰색으로 설정한다. PNG 알파 보존과 새로 그리거나 지울 때의 정책은 별개다.

[알파·내보내기 기록](evidence/ui-planning-alpha-export.json)을 남겼다. 이는 네이티브 인코더 재현이며 새 UI나 웹 출력의 추가 검증 완료를 뜻하지 않는다.

## 4. 투명 배경의 동작 계약

### 세 종류의 상태

| 상태 | 의미 | 저장 위치 |
| --- | --- | --- |
| 문서 픽셀 알파·지우기/확장 바탕 | 실제 작품 데이터와 새 영역의 기본 픽셀 | 기존 State와 RPAINT01 |
| 체커보드·흰색/회색 미리보기 | 투명 영역을 구별하는 화면용 바탕 | UI 설정, 이미지에 기록하지 않음 |
| 스킨·조작부 반투명 | 앱 버튼·패널의 외형 | UI 설정, 문서와 무관 |

새 그림 대화상자에는 크기와 `흰색 / 투명`을 명시한다. 첫 기본값은 기존 호환성을 위해 흰색을 유지하고, 사용자가 고른 새 문서 기본값은 별도 환경설정으로 기억할 수 있다. 투명 문서는 background 알파 0, 초기 레이어 픽셀 알파 0으로 만든다.

기존 그림의 배경 설정을 투명으로 바꿔도 이미 칠해진 흰색 픽셀이 자동으로 사라지지 않는다. 현재 ‘배경’ 레이어는 일반 레이어이며 그림이 함께 들어갈 수 있다. 이 레이어를 숨기는 명령을 ‘투명 배경으로 변환’과 동일하게 취급하지 않는다. 기본 개선에서는 흰 픽셀 일괄 삭제를 자동 실행하지 않는다. 실제 알파는 체커보드와 내보내기 미리보기에서 확인한다.

### background 책임 정리

단일 레이어의 지우개·잘라내기/선택 들기·삭제·전체 지우기와 캔버스 확장은 문서의 지우기 바탕을 사용한다. 다중 레이어의 현재 투명 삭제 동작과 기존 불투명 문서의 결과는 보존한다.

보조색은 우클릭 그리기·도형 채우기·문자 배경·색 교체에 사용한다. 투명 문서에서도 보조색을 흰색처럼 유효한 색으로 지정할 수 있어야 한다. 이를 위해 Canvas의 보조색을 문서 clear 색과 독립시킨다. `MainWindow::sync()`가 매번 덮어쓰는 연결도 제거 대상이다. 실제 파일 열기/새 그림/복구 때만 보조색의 초기화 정책을 적용한다.

기존 `배경색…` 및 우클릭 색상표 동작은 불투명 문서에서 결과가 달라지지 않도록 호환 경로를 유지한다. 새 UI에서는 `보조색`과 `문서 지우기·확장 바탕`을 별도 이름으로 드러낸다. 기존 명령을 조용히 다른 의미로 바꾸지 않는다. 투명 문서에서 보조색 변경이 알파 0인 문서 바탕을 불투명으로 바꾸지 않는지도 검증한다.

RPAINT01 필드를 추가하거나 background를 합성 배경 레이어로 재해석하지 않는다. UI 보조색은 기존 파일에 새 필드로 넣지 않는다. 불필요한 파일 마이그레이션을 피하고, 기존 background 값은 기존 문서의 지우기/확장 의미를 유지한다.

### 내보내기

| 출력 | 제안 동작 |
| --- | --- |
| PNG | 실제 픽셀 알파 유지. 체커보드·스킨은 제외. `투명도 유지` 상태 표시 |
| JPG/BMP | 이 앱의 불투명 출력 경로에서 합성할 바탕색을 명시. 흰색 기본값과 색 선택·미리보기 제공 |
| RPAINT01 | 레이어·background 알파 유지, 기존 형식 사용 |

바탕색은 문서 픽셀을 먼저 지우거나 바꾸는 방식으로 적용하지 않는다. 내보내기 후보에만 합성한다. 취소·인코딩 실패·다운로드 준비는 dirty·Undo/Redo·pending 편집을 바꾸지 않아야 한다. 기존 공개 C++ 저장 함수 호출은 유효한 기본 동작을 유지하며, 옵션 전달이 필요하면 기존 진입점을 보존한 최소 확장으로 처리한다.

## 5. 반응형 배치와 감지

### 감지 기준

우선순위는 사용 가능한 창의 논리 폭/높이 → 입력 능력 → 명시적 사용자 설정이다. UA의 mobile/tablet 문자열만으로 UI를 고정하지 않는다.

웹에서는 `ResizeObserver`, 필요한 경우 `visualViewport`, `matchMedia('(pointer:coarse)')`·`any-pointer`·hover·maxTouchPoints를 보조 정보로 사용한다. 실제 입력의 mouse/pen/touch는 현재 제스처 처리에 사용한다. 모든 정보를 하나의 ‘태블릿 여부’ boolean에 합치지 않는다. 네이티브는 Qt 창 크기, QScreen/DPR와 QPointingDevice 정보를 사용한다.

밀도 기본값은 터치 가능 환경에서 48 논리 단위, 마우스 전용에서 32~36이다. 자동/큰 조작부를 사용자가 선택할 수 있다. 손가락과 펜을 번갈아 쓸 때마다 버튼 크기를 바꿔 화면을 흔들지 않는다. 실제 입력이 진행 중이면 밀도·패널 재배치는 다음 안전한 시점으로 미룬다.

### 배치 초안

아래 수치는 웹 CSS px 및 Qt 논리 크기에서 검증할 초기 정책이다. 폰트 배율·가용 높이·실제 캔버스 잔여 폭을 함께 고려해 확정한다.

| 폭 | 명령과 도구 | 색상·레이어 | 화면 원칙 |
| --- | --- | --- | --- |
| 600 미만 | 상단 파일/되돌리기/내보내기, 하단 브러시·지우개·선택·색상·더보기 | 한 번에 한 개의 시트/전면 패널 | 종이에 최대 공간. 17개 도구를 세로로 고정하지 않음 |
| 600~839 | 접히는 도구 레일, 주요 명령 표시 | 필요할 때 여는 측면 패널. 세로/낮은 높이는 시트 | 태블릿 세로·분할 화면 대응 |

초기 열기·새 그림에서만 필요하면 맞춤 줌을 적용한다. 사용자가 고른 줌과 스크롤 중심은 회전·분할 화면·스킨 변경 후에도 유지한다. 자동 맞춤 상태인 경우에만 새 가용 영역에 맞춰 다시 계산한다. 문서 픽셀 크기를 화면 크기에 맞춰 축소하지 않는다.

스킨이나 layout 변경으로 Canvas/QTextEdit를 파괴하거나 다시 생성하지 않는다. 도구·레이어의 실제 QWidget/QAction을 재사용하고 패널 소유권 이동은 명시적으로 관리한다. 모바일 모달에서는 배경 캔버스 입력을 막고, 닫힘 뒤 원래 초점으로 돌아간다. 크기 변경 시 스크롤·줌·현재 레이어·선택·문자가 유지되어야 한다.

### 화면 안전 영역과 파일 UX

웹 호스트에는 viewport-fit, 네 방향 safe-area inset, 동적 높이의 fallback을 검토한다. 가상 키보드에서 `dvh`만으로 해결된다고 가정하지 않고 visualViewport의 높이·offset과 Qt 컨테이너 크기를 한 경로로 갱신한다. 중복 inset 적용을 피한다. 주소창 접힘·회전·홈 인디케이터·IME 입력을 실제 기기에서 확인한다.

긴 안내는 컴팩트 모드에서 도움말로 옮긴다. Mac 단축키 안내는 터치 화면 상단을 계속 점유하지 않게 한다. 내보내기 결과의 `파일 받기`는 화면에 보이는 주요 동작으로 유지하고, 패널을 밀어 문서 영역이 좁아지지 않게 재배치한다. 다운로드 준비와 저장 완료의 구분은 보존한다. 복구 목록·파일명·오류 대화상자는 가용 폭 안에서 줄바꿈/말줄임과 스크롤을 지원한다.

## 6. 터치·펜·마우스의 소유권

현재 앱의 마우스/펜 소유권 검사를 확장하고, 두 손가락 탐색을 같은 Canvas 입력 상태에서 처리한다. Qt의 터치→마우스 합성과 중복 처리하지 않도록 수신/accept 정책부터 검증한다.

| 입력 상태 | 제안 정책 |
| --- | --- |
| 마우스/펜 한 개 | 해당 장치가 현재 획 소유. 기존 동작 유지 |
| 손가락 한 개 | 손가락 그리기가 켜져 있으면 그리기, 꺼져 있으면 화면 이동 |
| 손가락 그리기 중 두 번째 접촉 | 미확정 손가락 획을 버린 뒤 두 손가락 탐색 시작. 점·짧은 선이나 Undo 항목을 남기지 않음 |
| 손가락 두 개 | 중심 기준 이동·확대. 문서 픽셀과 revision을 변경하지 않음 |
| 두 손가락 중 하나를 뗌 | 남은 접촉으로 바로 그리기를 시작하지 않음. 모두 놓아야 새 그리기 가능 |
| 펜으로 그리는 중 손가락 접촉 | 기본적으로 획에 간섭하지 않음. 펜이 닿은 동안 탐색으로 전환하지 않음 |
| cancel·capture 상실·페이지 비활성 | 소유한 미확정 제스처만 정리. 늦게 온 이벤트가 다음 획을 취소하지 않도록 세대 확인 |

‘펜만 그리기/손가락 그리기’는 보이는 설정으로 제공한다. 브라우저 정보만으로 완전한 팜 리젝션을 약속하지 않는다. 줌 ±·맞춤·수치 입력은 제스처 대안으로 남긴다. 두 손가락 탭 Undo 같은 추가 제스처는 첫 범위에서 강제하지 않는다.

주의할 실제 SDK 경계가 있다. 고정 Qt 소스의 `qwasmwindow.cpp:859–887`은 pen의 down/move/up을 처리하지만 cancel은 그 분기에서 반환한다. 앱의 UngrabMouse 검사만으로 브라우저의 모든 pen cancel을 처리한다고 단정할 수 없다. 전용 재현 시험을 먼저 만들고, 필요하면 BrowserBridge를 통해 소유 제스처와 세대를 확인하는 취소 통지를 추가한다. DOM과 Qt가 각각 획을 그리는 두 경로를 만들지 않는다.

Qt SDK에는 이미 `.qt-screen div { touch-action:none }`이 있다. 바깥 CSS에 같은 속성을 추가하는 것만으로 핀치 처리가 완성되지 않는다. 보조공학의 페이지 확대를 앱 전체에서 금지하지 않고, 캔버스 입력 영역과 HTML 파일 조작부를 구분한다.

coalesced 입력·예측 점은 실제 지연 측정 후의 후속 최적화다. 지원하지 않으면 일반 입력으로 동작하고, 예측 점을 저장 픽셀에 확정하지 않는다. 우선은 Qt SDK 수정 없이 해결한다. SDK를 수정한다면 현재의 ‘수정 없는 공식 Qt 소스 링크’ 정책과 대응 소스 제공도 함께 재검토해야 한다.

## 7. 스킨 구조

### 기본 두 스킨

| 요소 | Studio Dark | Classic 98 |
| --- | --- | --- |
| 표면 | 현재의 어두운 중립 작업 공간 | 회색 표면, 밝고 어두운 모서리의 입체 테두리 |
| 선택 강조 | 파란 강조와 명확한 선택 표시 | 남색 강조, 눌린 버튼과 점선 초점 |
| 형태 | 완만한 모서리와 간결한 선 | 직각 모서리, 절제한 입체 버튼 |
| 도구 아이콘 | 정돈된 선/실루엣, 필요한 부분의 보조 표시 | 동일한 의미의 직접 제작한 컬러/픽셀풍 표현 |
| 배치 | 화면 크기 정책 적용 | 동일 정책 적용. 넓은 화면은 전통적인 두 열 도구판을 선택 가능 |
| 터치 | 48 논리 단위 표적 | 같은 표적 유지. 과거의 작은 클릭 영역까지 재현하지 않음 |

한글 레이블은 읽기 쉬운 글꼴을 유지하며 픽셀풍 장식 때문에 작은 글자를 강요하지 않는다. 처음부터 별도 Win98 화면 전체를 복제하지 않는다. Qt Fusion을 공통 기반으로 유지하고 palette·QSS·아이콘 스타일을 바꾼다. QStyleFactory의 플랫폼별 스타일 이름이 항상 설치됐다고 가정하지 않는다. Windows 원본 리소스를 배포물에 복사하지 않는다. Studio Light/System 연동은 두 스킨의 대비와 상태 검증이 끝난 뒤 추가한다.

### 상태와 토큰

안정적인 `SkinId`와 작은 `UiPreferences` 값 구조를 MainWindow가 소유한다. 공통 토큰은 surface/workspace/text/muted/border/accent/disabled/focus, 버튼 크기, 아이콘 크기, 모서리, 테두리 깊이 정도로 제한한다. 작품의 전경색·보조색·텍스트 글꼴은 UI 토큰에서 덮어쓰지 않는다.

색상·크기가 Qt와 웹 호스트에서 따로 달라지지 않도록 선택된 SkinId와 허용된 토큰을 BrowserBridge로 전달한다. 웹 헤더·다운로드·오류·Qt 제목 표시줄도 같은 스킨을 따른다. 처음 로딩 중 플래시를 줄이기 위해 웹 설정의 초기 읽기 순서도 정한다. 기존 shadow DOM 클래스 의존성은 SDK 버전별 확인 대상으로 남긴다.

스킨 전환은 document revision·dirty·Undo/Redo·픽셀·pending 선택/문자를 바꾸지 않는다. 펜/손가락 획과 IME 조합 중에는 파괴적인 재배치를 지연한다. 알 수 없는 SkinId와 저장 실패에는 기본 Studio로 동작한다. OS 파일 대화상자는 플랫폼 외형을 따를 수 있다.

네이티브는 QSettings를, 웹은 기존 BrowserBridge 안의 작은 설정 operation과 `mypaint.ui.v1`처럼 앱 전용 이름의 저장소를 우선 검토한다. QSettings의 Wasm 저장 형식도 후보지만 웹 호스트의 선행 테마 읽기와 일관된 형식이 가능한지 확인 후 한 방식을 선택한다. 두 저장 체계를 중복 운영하지 않는다. 설정 저장 거절·private 모드에서는 현재 세션 적용을 유지하고 그림 작업을 막지 않는다. `.rpaint`에는 스킨·배치 환경설정을 넣지 않는다.

외부 CSS/JS·임의 스킨 파일 실행·런타임 아이콘 CDN은 도입하지 않는다. 내장된 스킨 ID만 허용한다.

## 8. 아이콘을 한눈에 구분하기 위한 계획

현재 도구 정의의 Tool/name/QAction을 기준으로 icon id·그룹·설명·단축키를 연결한다. 같은 동작을 모바일·메뉴·도구판에서 재사용한다. 단축키를 공통 QAction으로 옮긴다면 캔버스에만 적용해 HEX/문자 입력을 가로채지 않는지 검증한다.

| 도구/명령 | 개선할 형태와 이름 |
| --- | --- |
| 브러시 / 연필 | 뚜렷한 붓털·손잡이와 뾰족한 연필 끝을 구분 |
| 지우개 / 색 지우개 | 일반 지우개와 색 표적·교체 표시를 구분. 기존 색 지우개는 특정 전경색을 보조색으로 바꾸므로 ‘지정 색 교체’처럼 동작을 설명 |
| 채우기 / 스포이트 | 기울어진 통과 떨어지는 잉크, 채집관 끝을 구분 |
| 직선 / 곡선 | 두 끝점의 직선, 제어점이 보이는 곡선 |
| 사각 선택 / 자유 선택 | 점선 사각형, 닫힌 올가미 |
| 화면 이동 | 손 모양과 ‘화면 이동’ 이름. 선택 객체의 이동과 구분 |
| Undo / Redo | 현재 앞/뒤 삼각형을 굽은 화살표로 바꿔 페이지 이동과 구분 |
| 레이어 작업 | `합`은 아래 병합, `Aa`는 이름 변경의 명확한 형태와 메뉴 라벨로 교체 |
| 투명 배경 | 체커보드 + ‘투명’ 라벨. 흰색 스와치와 구분 |
| 저장 / 내보내기 | 네이티브 저장, 웹 프로젝트 다운로드, 이미지 내보내기를 각각 정확한 이름으로 표시 |

24 기준 벡터 도형의 광학 크기와 선 굵기를 맞춘다. 1x/2x/3x를 포함하고, 필요하면 비정수 DPR에서도 확인한다. Studio의 전체 SourceIn 단색 덮기를 고정 규칙으로 사용하지 않는다. 선택/비활성/초점 상태는 색 외에도 배경·테두리·체크·이름으로 구분한다. 스킨을 바꾸면 캐시 키에 맞춰 아이콘을 다시 생성한다.

우선 기존 QPainter 방식의 직접 제작 도형을 정리해 QtSvg 의존성을 추가하지 않는다. SVG 라이브러리를 실제 채택한다면 필요한 소수 자산만 고정 버전으로 로컬 포함하고 라이선스·QtSvg 플러그인과 웹 크기 증가를 확인한다. 아이콘 폰트·이모지로 대체하지 않는다.

PC는 툴팁에 이름·단축키를 제공한다. 터치에서는 현재 도구 이름을 항상 보이고, ‘더보기’는 아이콘+이름 그리드를 사용한다. 길게 누르기는 보조 설명이며 기능을 찾는 유일한 방법으로 만들지 않는다. 키보드 초점과 접근성 이름을 부여한다. Qt Wasm DOM의 이름 전달 제약은 실제 보조공학으로 별도 확인한다.

비용 S/M/L은 현재 구조에서 상대적인 구현·회귀 범위다. 실제 기기에서의 입력 문제는 별도 변동 요인이다.

| 우선순위 | 작업 | 위험 / 비용 | 완료 조건 |

| P1 | 표시 토큰·공통 아이콘·스킨 상태 | 중간 / M | 두 스킨에서 동일 문서·명령 동작, 설정 실패 시 편집 가능 |
| P1 | 컴팩트/중간/넓은 배치·대화상자 | 높음 / L | 390px에서 핵심 명령과 종이 공간 확보, 가로 화면/회전 보존 |
| P1 | 터치 밀도·제스처·펜만 설정 | 높음 / L | 펜과 손가락 혼용, 취소, 합성 입력 시험 통과 |
| P1 | 아이콘 이름·초점·수치 대안 | 중간 / M | 터치에서 hover 없이 식별, 주요 조작부 48 목표, 키보드/보조공학 검증 |
| P2 | 예측/병합 입력·추가 스킨·재질 효과 | 중간 / M~L | 측정된 체감/성능 이득이 있고 호환 fallback 유지 |

## 10. 단계별 작업 순서

### 단계 0 — 기준과 입력 spike

현재 미커밋 Studio 변경과 배포 산출물을 기준으로 고정한다. 이번 측정 자료를 회귀 기준으로 보존한다. 투명 저장/리사이즈/취소와 펜 cancel·멀티터치 합성 경로의 재현부터 준비한다. 실제 iPad와 Android 기기 확인을 조기에 진행해 SDK 제약을 뒤늦게 발견하지 않게 한다.

### 단계 1 — 투명 문서와 내보내기

새 그림의 흰색/투명 선택, clear 바탕과 보조색의 경계, 삭제/지우개/확장, PNG 열기 후 정책, JPG/BMP 바탕색을 함께 작업한다. 기존 RPAINT01과 네이티브 파일 교체 경로를 유지한다. 기존 흰 문서와 투명 문서의 동작 표를 먼저 테스트로 고정한다.

### 단계 2 — 공통 표시 기반과 아이콘

MainWindow에 흩어진 palette/QSS와 아이콘 생성의 반복 의미를 작은 `appearance.h/.cpp` 같은 paintui 소유 단위로 옮긴다. 실제 두 스킨에서 공유하는 표시 작업만 분리한다. 버튼 하나당 wrapper·ThemeManager/Repository/Service 계층을 추가하지 않는다. 현재 Studio와 새 Classic이 같은 QAction을 사용하도록 한다. 저장과 웹 초기 적용의 실패 fallback을 포함한다.

### 단계 3 — 반응형 셸

MainWindow의 resize와 웹 컨테이너 변경이 공유하는 소유 함수에서 배치를 적용한다. 실제 화면 크기별로 속성·레이어 패널과 명령을 재배치하고 Canvas는 유지한다. 컴팩트 파일 메뉴와 다운로드 바, 복구 목록, 오류/확인창까지 포함한다. 두 스킨과 큰 밀도에서 함께 확인한다.

### 단계 4 — 터치·펜 제스처

Canvas의 기존 이벤트 경계에서 터치 상태·소유 접촉·세대를 관리한다. Qt accept/합성을 한 경로로 처리한다. 필요할 때만 BrowserBridge에 취소/가용 영역 통지를 추가한다. 펜 필압, 두 손가락 줌 중심, 남은 한 손가락의 유령 획 방지, 보조공학 확대를 확인한다.

### 단계 5 — 통합·성능·문서·산출물

네이티브·웹 자동 검사와 실제 기기 인수를 마친다. 큰 DPR의 화면 버퍼·4MP 문서·다중 레이어·내보내기/복구 시 메모리와 긴 프레임을 측정한다. 스킨 효과 때문에 입력 지연이 늘면 효과부터 줄인다. 렌더 배율 제한을 도입하더라도 실제 그림 해상도는 바꾸지 않는다.

사용법·스킨·제스처·지원 한계를 갱신한 뒤 마지막에 웹 산출물을 생성한다. 현재의 별도 홈페이지 폴더와 manifest 검증·prune 정책을 유지한다. 새 스킨을 이유로 별도 Wasm 복사본을 배포하지 않는다. commit/push는 별도 요청에 따른다.

## 12. 인수 기준

### 데이터와 파일

- 기존 불투명 `.rpaint`를 열고 편집·지우기·확장·저장한 결과가 기존 계약과 동일하다.
- 투명·반투명 픽셀이 PNG와 `.rpaint` 왕복에서 보존된다. 체커보드 색 변경은 출력 바이트의 의미를 바꾸지 않는다.
- 단일/다중 레이어의 지우기·선택 들기·잘라내기·붙여넣기·크기 변경을 확인한다. 흰색 픽셀의 자동 삭제가 없다.
- JPG/BMP는 선택한 불투명 바탕색 위에 정확히 합성된다. 취소/실패는 원본 파일과 현재 문서를 유지한다.

### UI와 입력

- 최소 320·360·390·600·768·840·1024·1280·1440 폭과 낮은 가로 높이를 확인한다. 경계 전후와 200% 확대/큰 글자도 포함한다.
- 각 스킨 × 컴팩트/넓은 배치 × 터치/마우스 밀도에서 열기·Undo·내보내기·레이어에 접근할 수 있다. 회전으로 모달 확정 버튼이 화면 밖에 남지 않는다.
- 스킨/배치 변경 전후 revision, dirty, Undo/Redo, 레이어 픽셀, pending 편집을 비교한다. IME 조합과 HEX 편집도 유지한다.
- 두 손가락 시작/종료, 펜+손가락, 취소·capture 상실·앱 전환, 늦은 이벤트, 중복 합성을 시험한다.
- iPhone Safari, iPad Safari+펜+분할 화면, Android Chrome+가능하면 펜, 터치 노트북과 네이티브 마우스/트랙패드에서 실제 입력을 확인한다. 에뮬레이션을 실제 기기 시험으로 보고하지 않는다.
- VoiceOver/TalkBack와 데스크톱 키보드에서 도구 이름·선택 상태·초점 복귀를 확인한다. 드래그 외 수치/버튼 대안을 제공한다. 텍스트·아이콘·초점 대비를 스킨별로 확인한다.

### 저장소와 성능

- 설정 거절·잘못된 설정·새 버전의 알 수 없는 enum은 기본값으로 복구되며 작품을 열고 저장할 수 있다.
- 기존 IndexedDB 복구와 다운로드 URL 정리는 유지한다. 모바일 OS의 탭 강제 종료까지 마지막 미확정 획을 복구한다고 약속하지 않는다.
- 첫 로딩·획 처리·줌·복구·내보내기 시간을 실제 기기에서 기록한다. 효과 추가 전후를 비교하고, 근거 없이 특정 FPS/무지연을 완료 조건으로 선언하지 않는다.
- 네이티브 CTest와 필요한 sanitizer, 웹의 파일/선택/권한/손상/복구 회귀를 실행한다. 현재 계획 단계에서는 제품 코드 변경이 없어 전체 CTest를 재실행하지 않았다.

## 13. 완료 범위와 다음 구현 단위

이번에 완료한 것은 코드 확인, 공식 가이드 조사, 네 가지 크기의 현재 웹 화면 재현, 기존 네이티브 코어의 투명도 출력 재현과 이 계획이다. 실제 제품의 투명 배경 UI·반응형 배치·스킨 선택·새 아이콘은 아직 적용하지 않았다. 기존 미커밋 작업은 유지했으며 새 Git commit·push·배포를 실행하지 않았다.

첫 구현 단위는 ‘투명 문서/내보내기 안전성 및 입력 취소 재현’이다. 투명도 경계를 고정한 다음 표시 토큰과 공통 아이콘을 정리하면 두 스킨과 화면 크기 대응을 같은 UI 위에 안전하게 올릴 수 있다.
