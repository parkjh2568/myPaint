# Tauri에서 GPUI로 전환할 때의 영향과 myPaint 적용 판단

2026-11-15 · myPaint Studio 0.2.0 · `codex/studio-recovery`의 `48e4058` 및 후속 작업 트리

**현행 Tauri를 유지하고, 브러시 지연과 대형 캔버스의 렌더 비용을 먼저 계측하는 방향을 권장한다.** GPUI는 WebView 초기화와 런타임 비용을 없애고 화면 합성 경로를 Rust에서 직접 제어할 수 있다. 실제 전환 사례에서 시작 시간과 메모리가 개선됐다. myPaint는 브러시 획을 이미 WebView 내부에서 처리하므로, 매 프레임 Rust에서 화면 데이터를 전달하던 앱의 개선 폭을 적용할 수 없다. [현재 구조](../STUDIO_ARCHITECTURE.md) · [LegendApp 벤치마크](https://github.com/LegendApp/framework-benchmarks#latest-results) · [Cap 전환 사례](https://cap.so/blog/rebuilding-cap-in-gpui#performance)

GPUI의 폰트·GPU·첫 장면 준비 비용은 남는다. 시작과 작은 앱 메모리가 줄어들 여지가 있고, 실제 차이는 프로세스 그룹 전체와 cold/warm을 나눠 비교해야 한다. [Tauri 프로세스](https://v2.tauri.app/concept/process-model/) · [WebView2 프로세스](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-model) · [WebView2 성능](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance) |
| 렌더·입력 지연 | Chromium 기반 WebView의 합성은 GPU를 사용할 수 있고 Canvas 경로는 구현과 설정에 따라 달라진다. 브라우저 위에서 이미 완료되는 편집은 Rust 호출 비용을 매 이벤트마다 내지 않는다. | macOS Metal, Windows DirectX 같은 플랫폼 경로를 사용한다. 텍스처·업로드·프레임 예약을 조정할 수 있다. 프레임별 복사를 줄일 때 효과가 크고, 전체 래스터 업로드나 작업 스레드 대기가 남으면 지연도 남는다. 화면 갱신 주기, 큐, 드라이버와 합성기까지 포함해 검증한다. | 저장·파일 연산 | JS에서 Rust 호스트로 호출하는 작업은 IPC를 거친다. 알고리즘과 I/O는 호출 경계 안에서 별도의 비용을 낸다. | 같은 Rust 프로세스에서 직접 호출하도록 설계할 수 있다. 파일 인코딩, 원자 교체, 외부 파일 변경 검사, 차단 I/O 격리와 취소는 여전히 필요하다. 프로세스 경계 개선과 연산 자체 개선은 별도 측정한다. [Tauri IPC](https://v2.tauri.app/concept/inter-process-communication/) |
| 패키지·오프라인 설치 | Tauri는 시스템 WebView를 활용한다. Windows 런타임이 없을 때 bootstrap 다운로드를 선택하거나, 오프라인 설치 프로그램·고정 런타임을 포함할 수 있다. | WebView 설치 조건은 빠진다. 순 결과는 renderer·셰이더·자산과 빌드 옵션에 따라 달라진다. 짧은 다운로드, 설치 후 크기, 별도 런타임 필요 여부를 각각 비교한다. OS별 패키징·코드 서명도 검증한다. [Tauri Windows 설치 옵션](https://v2.tauri.app/distribute/windows-installer/#webview2-installation-options) |
| 조작·접근성 | 브라우저의 입력 컨트롤, 포커스와 키 탐색, DOM/ARIA를 사용한다. 앱에서 구현한 메뉴·탭·Canvas의 조작과 접근성은 별도 검증한다. | AccessKit 경계가 있으며, 새 UI의 역할·이름·상태·키 동작과 접근성 트리를 작성한다. 세 출처에서 macOS 시작 또는 메모리 이점을 확인했다. 비교 대상은 UI 시작, 목록, 영상 재생이며, Windows의 같은 래스터 편집기에서 펜 입력부터 픽셀 표시까지 측정한 공개 대조 결과는 확인하지 못했다. Zed도 GPUI에서 기기별 120Hz 프레임 드롭을 재현해 프레임 예약과 macOS 합성 경로를 조정했다. [Zed의 120Hz 프레임 조사](https://zed.dev/blog/120fps)

**GPU 이미지 전달은 OS별로 확인해야 한다.** GPUI의 일반 `paint_image`는 CPU의 이미지 바이트를 텍스처 아틀라스에 넣는다. 검토한 upstream `main`에서 `paint_surface`는 Apple용 `CVPixelBuffer` 경로를 제공하며, Windows의 `draw_surfaces`는 해당 표면을 그리지 않는다. Windows에서도 일반 이미지와 GPUI UI는 DirectX 경로로 그린다. 영상·그림 편집기에서 별도 GPU 텍스처를 무복사로 연결하려면 실제 백엔드와 API를 먼저 검증한다. 웹 기능과 IME·접근성 경로는 Zed 제품의 고정 커밋 `e8bc16a`에서도 교차 확인했다. 현재 Windows 패키지에서 추출한 앱의 2048×2048·16레이어 장면은 Canvas 1381×1002, DPR 1.5 조건에서 캐시가 빈 첫 렌더 **107.5ms**, 변경 영역 적용 **16.1ms**, 변경 없는 상태 **0.2–0.7ms**가 걸렸다. 첫 호출은 96회 업로드와 약 38.1MiB의 `putImageData` 입력을 기록했고, 변경 없는 표본에서 업로드가 없었다. 측정 범위는 렌더 호출 본문이다. 첫 장면에서는 WebView 초기 비용과 RGBA 복사·캐시 준비를 각각 추적할 가치가 있다. 이 장면과 8192×4096·2레이어 장면 모두 권위 RGBA만 256MiB로, 히스토리·작업 버퍼·GPU 메모리까지 포함한 피크는 UI 유휴 메모리와 별개의 지표다. [Windows 검증 부록](audit/VERIFICATION_AND_DELIVERY.md#실행-결과) · [스모크 계측 구현](../../web-app/src/platform/native-smoke.ts#L192) · [최대 문서 검증](../../web-app/tests/max-document.mjs)

현재 로컬 Windows x64 NSIS 설치 파일은 약 **2.10MiB**, 추출한 앱 exe는 약 **9.52MiB**다. 기존 시스템 WebView 런타임의 설치 용량이나 부재 시 다운로드 용량은 이 두 숫자에 포함되지 않는다. 작은 다운로드만을 목표로 할 경우 GPUI 이식의 우선순위는 낮다. [Windows 검증 대장](../CURRENT_STATUS.md#windows-x64-설치-패키지와-앱-실행-후속-검증)

## 권장 방향과 검증 조건

웹과 데스크톱의 기능 동등성이 중요하면 Tauri의 공유 UI가 유지보수에 유리하다. 데스크톱 전용 신규 앱에서 Rust 편집 엔진이 이미 있고 자체 GPU의 프레임 전달이나 WebView 초기화가 실제 병목이라면 GPUI가 합리적인 후보가 된다. myPaint의 경우 브러시 경로가 WebView 안에 있고 웹·모바일 배포가 있으므로, Tauri 안의 작은 최적화가 전환보다 먼저 검증할 가설이다. [현행 배포 범위](../../PROJECT_HANDOFF.md) · [Cap 전환의 렌더 경로](https://cap.so/blog/rebuilding-cap-in-gpui#getting-video-frames-to-the-screen)

1. **현행 안정화와 기준선 측정.** 여러 탭의 닫기·종료 취소와 열린 프로젝트의 내보내기 보호를 먼저 바로잡는다. Windows 60/120Hz와 목표 macOS 기기에서 시작 후 그리기 가능 시점, 첫 획의 디스플레이 표시, 연속 획과 확대·이동의 p50/p95/p99, 프레임 누락, 앱·WebView 전체 private memory와 GPU 메모리, 유휴 CPU를 나눠 기록한다. 같은 해상도·DPR·전원·파일·브러시 보정으로 비교한다. 서술한 Windows 수치는 기존 참고선으로 보존한다. [코드베이스 재감사](STUDIO_CODEBASE_REAUDIT.md) · [WebView2 추적](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/performance) · [PresentMon 지표](https://github.com/GameTechDev/PresentMon/blob/main/README-CaptureApplication.md#metric-and-csv-column-definitions)
2. **병목을 좁혀 비교.** 동일한 RGBA·획 목록과 바뀐 타일만 먹이는 렌더 테스트로 WebView Canvas와 GPUI 표시 비용을 비교한다. 별도의 편집 테스트로 입력→픽셀 연산→업로드→표시를 분리한다. 문서 열기와 저장은 동일한 디스크·압축 설정에서 codec, 호스트 전달, 원자 쓰기를 나눠 잰다. Present 이벤트는 표시 시점의 도구 추정으로 쓰고 실제 펜이 화면에 보이는 시점은 고속 촬영으로 대조한다. 800×600 일반 그림과 2048²·16레이어 장면을 둘 다 쓰고, 초기화 여부와 전체/부분 타일 업로드를 따로 기록한다. [PresentMon 지표](https://github.com/GameTechDev/PresentMon/blob/main/README-CaptureApplication.md#metric-and-csv-column-definitions) · [입력·표시 지연 용어](https://developer.nvidia.com/blog/understanding-and-measuring-pc-latency/)
3. **전환 기준을 정하고 작은 실험으로 판단.** 최적화한 Tauri에도 체감 문제가 남고, 같은 장비·장면에서 GPUI가 목표 지표를 반복 개선할 때 검토한다. 예를 들어 목표를 고주사율 기기의 획 지연으로 잡으면, 실기기 p95가 목표 주사율의 한 화면 주기에 해당하는 시간만큼 꾸준히 줄어드는지를 의사결정 기준으로 사전에 정할 수 있다. 별도 성공 조건은 저장 파일·픽셀 정확성, Undo/Redo와 복구, 실제 펜 필압·한글 IME·키보드 조작·고배율, 웹 지원 계획이다. CPU 변형이나 인코딩이 병목이면 해당 커널만 최적화하는 방향을 우선한다. 제품의 GPUI 빌드와 같은 작업의 A/B 계측은 아직 수행하지 않았다.
