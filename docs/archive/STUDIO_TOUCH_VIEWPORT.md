# 터치 조작과 입력 투영 보존

2026-11-06. [소스·재현·수정·독립 검증 근거](../evidence/studio-touch-viewport.json). QF-19/20의 확인된 문제를 수정한 단계이며 전체 전환·실기기·출시 완료를 뜻하지 않는다.

## 확인한 원인과 수정

| 위험 | 발생 조건과 영향 | 수정 |
| --- | --- | --- |
| Major: 입력 투영 소유권 | 드래그 중 화면 크기 변경 후 취소하면 원본/Redo는 복원되지만 예전 backing이 남아 첫 다음 클릭이 빗나갔다. 크기가 같고 원점만40px 이동한 뒤 손을 떼면 임시 연필 선17px가 잘못 확정됐다. | 보기의 원점·크기·DPR/backing을 추적하고 입력 시작·이동·resize 경계에서 확인한다. 실제 진행 중인 pointer 소유자의 임시 편집만 되돌린 후 기하를 갱신한다. |
| Minor: 편집 문자 가림 | 390×844→390×500에서 글상자49.25px가 가려졌다. 내용·캐럿·PNG 손상은 없었다. | 포커스된 글상자가 화면에 들어오도록 camera offset만 조정한다. 문자 크기나 줄바꿈 폭은 바꾸지 않는다. |
| Minor: 터치 CSS 충돌 | 헤더44px·줌26px·일부 입력44px와 팔레트/레이어 예외, 태블릿 레일 잘림이 있었다. 데스크톱 강제17px 스크롤바에서는48px 버튼 중42px만 보였다. | 터치 표적48px, 연결 label, 팔레트 자동 열 배치, intrinsic 레일 폭, 레이어 조작3×2와 패널 전체 스크롤을 함께 적용했다. |

진행 중 제스처의 투영이 바뀌면 provisional만 롤백하며, 손을 뗀 뒤 완료를 기다리는 비동기 선택 크기 변경은 취소하지 않는다. 취소 뒤 같은 변경을 한 번 소비하고 새 입력을 받는다. `pointerMove`는 갱신 뒤 소유권을 다시 확인하므로 예전 이벤트가 새 문서 좌표로 확정되지 않는다. 새 `viewLeft/Top`은 기존 `viewWidth/Height`와 같은 시점에 갱신한다.

정지 상태의 선택·문자와 수동 줌은 유지한다. 글상자가 화면보다 크면 시작 가장자리를8px 여백에 두며, 전체 캐럿 가시성까지 보장하지 않는다. textarea 노드·내용·client 크기·스크롤·선택 범위·조합 상태와 문서 좌표를 바꾸지 않는다. 정상 편집도 화면 변화 없이 매번 fit하지 않는다.

## 반응형 구조

터치 모드의 버튼과 입력은48px 기준을 적용하며 체크박스는 실제 연결 label을 조작 영역으로 사용한다. 마우스 모드의 작은 줌 컨트롤 등은 기존 밀도를 유지한다. 600px 이상 터치 도구 열은 `minmax(66px, max-content)`로 스크롤바의 실제 점유 폭을 수용한다. 휴대폰의 한 열 구조는 유지하고 320px에서는 제목을 별도 행으로 배치한다.

팔레트는48px을 만족하는 열 수로 배치하고, 레이어 조작은3열×2행으로 나눈다. 좁거나 낮은 화면의 inspector는 전체를 스크롤하며 닫기 헤더는 고정한다. 속성/레이어 버튼은 패널을 열고 요청한 구역으로 이동한다. 색상환의 backing440×420은 유지하고 CSS 높이만 화면에 맞춘다. 이 배치 변경에 새 helper나 모듈을 추가하지 않았다.

## 실제 검증

- 독립 Chrome20경로: 320/360/390px, 768px 태블릿, 844×390 가로, 1280px 마우스와 수동 터치, 두 스킨. 전체 제어 관측1,941건 중 터치1,659건이 모두48×48px 이상이며9705개 center/edge hit 검사가 통과했다. 같은 제어를 여러 상태에서 측정한 수치로, 고유 위젯·사용자 수가 아니다. 표적은 스크롤로 드러낸 뒤 실제 client clip과 `elementFromPoint`를 검사했다.
- 크기 변경 후 cancel/up, 동일 크기 원점 변경, 첫 다음 클릭·한 번의 Undo·원본·기존 Redo를 확인했다. 선택은 실제 빨간 marker가 움직이는 전체 literal PNG와 비교했다. 문자 PNG·125% 줌·client258×118·caret60..66·scrollTop48·내용과 합성 조합 이벤트 상태를 보존했다.
- 기존 단위229개, 포인터26개, 비동기 선택 크기 변경10개, 웹 회귀48개가 통과했다. 기존 격리 단위 fixture에는 새로 읽는 DOM/DPR 환경만 제공했고 검증 조건을 낮추지 않았다.
- 최종 macOS 앱의 실제 WKWebView·IPC·복구·코덱·종료·scene4단계와 정상 종료를 확인했다. 새20개 UI 조합의 WK/Windows/실제 터치 검증을 대신하지 않는다. 최종 타입·포맷·웹/앱/manifest 빌드도 통과했다.

네이티브 dialog는 Tab으로 브라우저 UI에 중립 포커스가 생길 수 있다. 별도 기본 HTML dialog와 같은 동작임을 확인했으며 앱 배경 포커스/실행은 허용하지 않고 다음 Tab의 모달 복귀를 검사한다. 앱에 강제 Tab trap을 추가하지 않았다. 설정 직후의 비동기 적용도 skin과 density를 모두 기다려 확인한다. 이 두 테스트 교정과 초기에 가시 변화가 없던 선택 fixture의 보강은 원문 기록과 구분해 보존했다.

## 성능과 변경 범위

기존 `point`가 한 이벤트의 직사각형을 재사용한다. 실제4/16/64개 합쳐진 샘플에서 동기 Canvas 좌표 읽기는 각각5/17/65회→1회였고, 세 쌍의 실제 PNG와 한 번 Undo가 같았다. 이는 호출 수 계측이며 강제 layout 시간·CPU·FPS·p95 개선 수치가 아니다.

런타임17개 중 main/CSS만 바뀌었다. 기존8메서드와 보기 원점 필드2개가 변경 범위이고 새 helper·런타임 모듈·의존성·Rust/엔진/형식 변경은 없다. 문자·도형·pending·내보내기 알고리즘은 AST로 이전과 동일하다. [최신 의존성 그래프](../evidence/studio-touch-viewport-module-graph.json)는 소스 runtime 순환0, 배포 정적 평가 순환0과 기존 동적 SCC2개를 확인했다.

최종 웹 payload는 LICENSE 포함9파일·285,903B이며 검증 manifest는 별도다. SDK·node_modules·Rust target은 포함하지 않는다. 고정 `final-bundle`과 최종 소스를 보존했으며 실제 홈페이지 쓰기·커밋·푸시·공개 배포는 수행하지 않았다.

## 남은 인수와 다음 순서

QF-19/20과 전체34태스크의 완료 체크는 유지한다. 전체 감사는6개 입증·26개 부분·2개 미구현이며 선행까지 닫힌 것은 QF-01뿐이다. 실제 Android 키보드·IME·회전, layout viewport는 그대로이고 VisualViewport만 줄거나 이동하는 모델, 큰 줌의 전체 caret 가시성, 실제 Windows/펜·터치·DPR/보조공학 인수는 남는다. 이번 창 크기/포인터/스크롤바/IME 조건은 통제된 브라우저 에뮬레이션이다.

후속은 VisualViewport 전용 키보드·브라우저 pan 정책의 재현, 미변형 선택 확정의 전체 복사와 자동 복구 비용 실측이다. 물리 장치·OS 파일/IME·공개 CI·서명/공증·복구 인계·Pages 전환 게이트도 분리한다. 모바일·태블릿은 웹 전용이고 실행 파일은 Windows/macOS 전용이다.
